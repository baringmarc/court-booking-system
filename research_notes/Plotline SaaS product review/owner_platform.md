# Owner operations and SaaS platform readiness

## What is already strong and what was actually inspected?

### Takeaway
Plotline already has a substantial operational core. The main opportunity is to make that core easier to run and support repeatedly, rather than add a broad collection of unrelated SaaS features. This review inspected current source, relevant migrations, test inventory, planning/handoff records, and three saved admin-tour screenshots. It did not log into production, run the gate, query live tenant data, or prove current deployment state.

### Cited Findings
- Venue administration already includes a guided draft setup checklist with links to fix courts/rates/hours/payments/photos and a server-read readiness condition before Publish. This is a good foundation for assisted onboarding; do not recommend building a checklist from scratch. [SetupChecklist.tsx](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/admin/SetupChecklist.tsx:7)
- The daily dashboard already shows proofs awaiting review, today's bookings, the next booking, a court-time grid, earnings and schedule. Walk-ins are an existing capability gated per venue by Plotline. [DashboardPage.tsx](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/admin/DashboardPage.tsx:89)
- Earnings already include date ranges, period comparisons, collected money by payment method, court/sport occupancy, daily charts, upcoming confirmed value, revenue/Plotline-fee split and CSV export. “Add analytics/CSV” would be an inaccurate generic recommendation. ### Inferences
- The strongest wedge is assisted setup and straightforward venue operations for Philippine court businesses, including manual payments; there is no evidence here that a rewrite, microservices, or native mobile application would address the most immediate weaknesses.
- UI polish has advanced faster than some operating procedures. The next work should emphasize reliable first use, day-to-day exception handling, and measuring business outcomes.

### Gaps
- No production uptime, current user count, support volume, booking conversion, venue retention, collection rate or current infrastructure spend was supplied or queried. No profitability, scalability ceiling, or security-certification claim can be made.
- Existing tests were inspected as evidence of intended coverage, not rerun. No full security audit was performed.
- Some planning documents contain historical “current” statements. Latest source is stronger evidence of shipped code, and another researcher has live website observations that may supersede deployment notes.

## Which improvements should be prioritized?

### Takeaway
Prioritize operational reliability and a simpler daily workflow. The following are recommendations, not approved scope. P0 means before relying on the platform for real venue operations; P1 means pilot-driven next work; P2 means add once observed demand justifies the complexity. Effort is relative, not a delivery estimate.

### Cited Findings

1. **P0 — Make releases a coordinated product operation across frontend, database, functions and marketing (medium effort).** Handoff explicitly records a November 6 production booking outage from a frontend calling `get_public_schedule` before its migration, and a November 7 console failure from missing migration/function deployment. These are historical documented incidents, not a claim the site is currently broken. The handoff also records subsequent repairs. [TASKS release records](/Users/macbookpro/Documents/Projects/court-booking-system/TASKS.md:14)
   - Recommendation: a release manifest pins the app commit, required migration IDs and functions, plus plotline-site contract compatibility; preflight refuses frontend publication when dependencies are absent. Add post-release public availability + owner sign-in/console read checks and a rollback procedure. Track deployed versions in one short current-state document, leaving history elsewhere.
   - Acceptance/metric: staging rehearsal and a deliberate missing-dependency test stop deployment; smoke evidence recorded after every release; no schema-mismatch incidents.

2. **P0 — Complete monitoring and prove recovery, including the customer journey (small–medium effort).** Uptime checks and the runbook remain explicitly postponed in TASKS. Proposed uptime checks only cover a public shell and Auth health, and the doc correctly notes a 401 proves a gateway response, not the database. The current restore checker treats matching public-table counts as success and does not restore Storage objects or exercise authentication, RLS, RPCs and payment-proof access. [TASKS T16.4–5](/Users/macbookpro/Documents/Projects/court-booking-system/TASKS.md:2219), [UPTIME.md](/Users/macbookpro/Documents/Projects/court-booking-system/docs/ops/UPTIME.md:9), [restore-check.mjs](/Users/macbookpro/Documents/Projects/court-booking-system/scripts/restore-check.mjs:24)
   - Recommendation: finish existing work, add a read-only availability check, email-outbox failures and backup-age alerts; run a restore rehearsal with nonempty photo/proof storage, schema/RLS/function checks and test booking lifecycle in a disposable environment. Define acceptable data loss and recovery time with the business.
   - Acceptance/metric: alert delivery demonstrated; one restore can display a recovered photo/proof and pass a local booking workflow; actual recovery duration recorded. Keep backups outside Supabase: official docs confirm database backups omit Storage objects. [Supabase backups](/Users/macbookpro/Documents/Projects/court-booking-system/scripts/backup-production.mjs:50), [Official Supabase backup guide](https://supabase.com/docs/guides/platform/backups)

3. **P0 before first customer exit — Implement the promised offboarding and retention process (medium–large effort).** Public terms promise closing the booking page, a final invoice, 30 days of admin/CSV access, then venue-data deletion subject to retained records. The schema has a `closed` state, but the current console deletion API deliberately rejects any venue with booking/billing history. Repository search found guarded unused-venue deletion and separately reviewed test-history purge tooling, not a scheduled customer offboarding workflow. This is a process/product gap, not a legal conclusion or instruction to remove retention safeguards. [Public terms source](/Users/macbookpro/Documents/Projects/plotline-site/src/config/legal.ts:80), [Venue states](/Users/macbookpro/Documents/Projects/court-booking-system/supabase/migrations/20261030054219_venues_members_platform_admins.sql:14), [Deletion guard](/Users/macbookpro/Documents/Projects/court-booking-system/supabase/migrations/20261106180458_t17_26_guarded_deletion.sql:140)
   - Recommendation: a reviewed exit case tracks request date, closure, outstanding player commitments/refunds, final billing, export window, retention exceptions and completion evidence. Start with a documented manual runbook and reminders; automate only after policy is clear. Add a lead-retention review mechanism matching the “1 year after last contact” promise.
   - Acceptance/metric: a synthetic used venue can complete the lifecycle without losing retained invoice records or access earlier than promised; every request has an owner and due date.

4. **P1 — Make Dashboard a compact “Today” workspace; make Reports actually contain reports (small–medium effort).** The current order puts earnings before today's court grid and schedule; all three summary links go to the same bare `/admin/bookings` route, whose default is the proof queue. Thus clicking “Today's bookings” or “Next booking” does not select that day/booking. `Reports` routes to `StatementPage`, while business analytics and CSV remain on Dashboard. [Dashboard links/order](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/admin/DashboardPage.tsx:103), [Default filters](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/admin/bookingFilters.ts:26), [Reports route](/Users/macbookpro/Documents/Projects/court-booking-system/src/routes/router.tsx:80)
   - Recommendation: show urgent proof/refund items, next arrivals and day court calendar first; let the date change, and provide contextual add/open/reschedule actions. Deep-link today's count to today's all-status list and next booking to its actual record. Put Earnings, Occupancy, Exports and Plotline statement under clear Reports tabs. Move the owner manual into persistent Help with a small dashboard link. Retain the warm visual identity but reduce large card padding on phones.
   - Acceptance/metric: an owner finds a specific upcoming booking or today's free court in one or two actions; compare task time and scrolling in a moderated phone pilot. This is a UX recommendation, not measured conversion uplift.

5. **P1 — Add a refund/exception resolution ledger before automating refunds (medium effort).** Paid cancellations are warned about, rejected online payments are labeled Refund due, and duplicate-payment possibilities are flagged, but resolution is outside the app. `isRefundDue` is derived solely from rejected PayMongo status, so the product has no demonstrated “refund completed” state. Accepted money on cancelled bookings remains counted in takings by design. [ReviewPanel warnings](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/admin/ReviewPanel.tsx:65), [paymentFlags](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/admin/paymentFlags.ts:18), [SPEC cancellation behavior](/Users/macbookpro/Documents/Projects/court-booking-system/SPEC.md:104)
   - Recommendation: record refund required/not required, amount, reason, responsible staff, due date, external reference and settled timestamp; distinguish collected gross from refunds and net court receipts. Do not require live PayMongo refunds to ship this: manual refunds need tracking too.
   - Acceptance/metric: exceptions can be filtered and closed with an audit trail; show age of unresolved refunds and reconcile gross/refunds/net. Keep the original payment immutable.

6. **P1 before multi-staff rollout — Make roles operational, not merely labels (medium–large effort).** `venue_members` distinguishes owner and staff, but the main admin helper accepts any membership; many settings policies use that helper. The UI determines access from venue membership and the inspected admin routes have no team-management screen. Owner invitation is a platform-console function. [Admin helper](/Users/macbookpro/Documents/Projects/court-booking-system/supabase/migrations/20261030054219_venues_members_platform_admins.sql:45), [Settings RLS](/Users/macbookpro/Documents/Projects/court-booking-system/supabase/migrations/20261030062110_venue_scoped_rls.sql:1), [UI admin check](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/auth/useIsVenueAdmin.ts:4), [Owner invitation API](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/console/api.ts:51)
   - Recommendation: owner-managed staff invitations/revocation and a small permission matrix: desk operations versus prices/payment accounts/export/settings. Preserve tenant enforcement in the database; record who changed operationally sensitive settings. Avoid overbuilding arbitrary custom roles.
   - Acceptance/metric: desk staff can review permitted bookings but cannot change payout details or export customer data; revocation takes effect on subsequent operations; owner/staff/cross-venue tests cover each capability.

7. **P1 — Extend assisted onboarding through the first successful week (medium effort, partly service design).** Lead management is already status/notes/create-venue; draft setup checks technical readiness, but neither demonstrates successful real-owner activation or migration of existing reservations. Handoff says one real production owner invite remained unproven, which must be checked rather than treated as current fact. [LeadsPage](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/console/LeadsPage.tsx:16), [SetupChecklist](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/admin/SetupChecklist.tsx:27), [Handoff](/Users/macbookpro/Documents/Projects/court-booking-system/TASKS.md:13)
   - Recommendation: keep the intentional no-self-serve model. Add a platform activation checklist: existing reservations imported or entered; venue owner completes practice proof review; public schedule preview approved; first real paid/manual booking confirmed; first weekly reconciliation; response-time expectations agreed. Start with a guided import template/concierge migration, not a complicated migration engine. Lead follow-up due dates and assigned owner prevent interest disappearing in notes.
   - Acceptance/metric: lead-to-first-contact time, invite-to-first-login, time to publish, time to first confirmed booking, owner minutes/help requests per setup, week-one active venues.

8. **P1 discovery, P2 build — Support the repeating work that causes parallel spreadsheets (medium–large effort).** Recurring bookings are explicitly a non-goal today; open play is created as one session on one date. This is deliberate missing scope, not a defect. [SPEC non-goals](/Users/macbookpro/Documents/Projects/court-booking-system/SPEC.md:15), [OpenPlayForm](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/admin/OpenPlayForm.tsx:36)
   - Recommendation: ask pilot venues to enumerate standing weekly groups and open-play schedules. If common, first add Duplicate session/booking, then a finite recurring series with conflict preview, exceptions, and “this occurrence/future occurrences.” Define the per-booking-fee and cancellation semantics before implementation. Add arrival/check-in/no-show tracking only if it informs real staff decisions; absent types are not proof that every venue needs it.
   - Acceptance/metric: setup time for a month of recurring play; conflict visibility; reduction in reservations tracked outside Plotline. Do not jump directly to memberships, leagues or coaching products.

9. **P1 — Measure unit economics and operational adoption before changing price (small effort initially).** Shared facts say ₱10 per confirmed online transaction, paid by the player, with no setup/monthly/per-hour fee and no self-serve signup. Billing policy keeps player-cancelled confirmed fees, credits venue cancellations, and excludes walk-ins and open play. Invoices are manually reviewed and settled. [facts.json](/Users/macbookpro/Documents/Projects/court-booking-system/docs/facts.json:5), [Billing rules](/Users/macbookpro/Documents/Projects/court-booking-system/docs/SAAS-PLAN.md:109), [Invoice UI](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/console/InvoicesPage.tsx:12)
   - Recommendation: calculate contribution per active venue from collected booking fees minus attributable support/setup, email/storage/infrastructure and collection work. Also measure what share of real reservations is recorded in Plotline, distinguishing online bookings, enabled walk-ins and blackouts. Prefer accurate venue inventory and useful desk workflows to restrictions that push staff back into notebooks; walk-ins are now an existing per-venue switch, so evaluate pilot usage rather than propose removing it.
   - Arithmetic only, not revenue forecast: at the current fee, 100/300/1,000 billable transactions produce ₱1,000/₱3,000/₱10,000 gross fee charges before credits, costs, unpaid invoices or tax. Actual volumes and costs are unknown.
   - Acceptance/metric: monthly contribution estimate, support minutes per active venue, invoice collection time/rate, booking adoption; decide pricing only after evidence. These recommendations do not change the agreed fee.

10. **P1 — Separate live manual-pay readiness from future online-payment readiness (large effort for Phase 4).** The source specification explicitly says per-venue online-pay switches currently use the platform test-mode account; real venue-owned PayMongo credentials/health checks are planned Phase 4, not shipped live-payment capability. Existing manual proofs are the real pilot path. [SPEC switches](/Users/macbookpro/Documents/Projects/court-booking-system/SPEC.md:377), [Phase 4 plan](/Users/macbookpro/Documents/Projects/court-booking-system/docs/SAAS-PLAN.md:290)
    - Direct code verification: checkout reads one global `PAYMONGO_SECRET_KEY`, not a venue secret, and rejects a live key; `isTestSecretKey` accepts only the `sk_test_` prefix. The console explicitly warns that its switch enables the shared Plotline test-mode account. This makes unqualified public claims about venue-owned live automatic payments a present capability mismatch, regardless of unknown hosted switch configuration. [Checkout function](/Users/macbookpro/Documents/Projects/court-booking-system/supabase/functions/create-paymongo-checkout/index.ts:29), [Test key enforcement](/Users/macbookpro/Documents/Projects/court-booking-system/supabase/functions/_shared/paymongo.ts:20), [Console warning](/Users/macbookpro/Documents/Projects/court-booking-system/src/features/console/OnlinePaymentsControl.tsx:40)
    - Recommendation: state that boundary consistently in sales and onboarding. Deliver Phase 4 only when pilot demand warrants it, with a verified venue-owned account, account/webhook health, reconciliation and a real controlled payment/refund proof under separate release approval. A console toggle is not evidence that live payments are ready.
    - Acceptance/metric: each live-payment venue passes account-specific checkout/webhook/failure/refund testing; no venue can accidentally charge against the demo account.

### Inferences
- A refund ledger, contextual dashboard links and report information architecture offer immediate practical gains without broadening the product into a full club-management suite.
- The role model should be tightened before inviting front-desk employees widely. This is a least-privilege product recommendation, not evidence of a cross-tenant breach.
- Better unit economics may come from faster setup and less support work before any fee increase. Current data is insufficient to recommend subscription, percentage fee or higher booking fee.

### Gaps
- Team management, recurring series, offboarding and refund completion were not found in inspected UI/API/type inventory. Repository absence conclusions are scoped to this inspection; manual procedures elsewhere could exist.
- Current hosted migrations, live monitor setup, latest successful backup age and current PayMongo configuration were not independently checked.
- “Proof-review SLA,” “minutes saved” and “higher conversion” are proposed measurements, not measured benefits.

## What should the near-term roadmap and evidence standard be?

### Takeaway
Use the next pilot as a learning milestone with a small number of owners doing real work. Keep reliability and terms fulfillment ahead of feature breadth, and protect the useful engineering foundations already present.

### Cited Findings
- The two repositories already have a shared business-facts source and a compatibility contract; strengthening release/contract checks builds on the existing platform design. [PLATFORM.md](/Users/macbookpro/Documents/Projects/court-booking-system/docs/PLATFORM.md:1), [facts.json](/Users/macbookpro/Documents/Projects/court-booking-system/docs/facts.json:1)
- Operations readiness work is already queued as M16, so resume/finish it rather than record a duplicate “add monitoring” milestone. [TASKS T16.4–5](/Users/macbookpro/Documents/Projects/court-booking-system/TASKS.md:2219)
- Official Supabase documentation recommends off-site exports for free projects and explains both daily-backup recovery windows and Storage exclusions; the existing custom archive addresses Storage backup, but the restoration proof is narrower than the archive. [Supabase backup guide](https://supabase.com/docs/guides/platform/backups), [restore-check.mjs](/Users/macbookpro/Documents/Projects/court-booking-system/scripts/restore-check.mjs:1)

### Inferences
- Proposed timeboxes, contingent on capacity rather than promises: **first 30 days**, qualify payment claims, finish M16 monitoring/runbook, rehearse coordinated release and owner onboarding, fix dashboard deep links and Reports naming; **days 31–60**, pilot with two or three venues, add tracked refund resolution and minimum staff permissions, document/implement exit handling before a real customer needs it; **days 61–90**, use pilot evidence to choose recurring bookings/open-play improvements or venue-owned live payments, and review contribution economics.
- Proposed sequence: (1) release/runbook/monitoring and owner activation rehearsal; (2) dashboard/report navigation improvements, refund resolution, staff permissions; (3) two or three pilot venues with weekly follow-up and collected economics; (4) recurring/open-play improvements or Phase 4 based on repeated observed need.
- Suggested pilot evidence: first contact → invitation → first login → publish → first confirmed booking; median and slow-end proof review time; failed/expired booking recovery; weekly active owners; exceptions unresolved after an agreed interval; collected monthly fees versus support minutes. Use aggregate events without tokens or payment-proof contents.
- The admin visual style is distinctive and sufficiently coherent to iterate. Prioritize density, hierarchy and workflow predictability over another wholesale theme refresh.

### Gaps
- Priority order is advisory. Business urgency, existing customer commitments and pilot interviews could change it.
- No source/code changes were made by this audit; all conclusions should be discussed before converting them into SPEC/TASKS acceptance criteria.
